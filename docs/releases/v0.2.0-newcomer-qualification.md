# v0.2.0 newcomer qualification

Status: bounded newcomer rehearsal complete, October 16, 2026. This record
covers source commit `552e21f8881fe47c603b950ad9bd059a5398fd63`. It does not
establish release readiness.

The rehearsal used a source archive without `.git`, a new isolated Linux
server, and disposable accounts and device configurations on a separate Mac.
The archive built with Go 1.26.6 on both Linux and macOS. The Compose server
was healthy. Two invited members claimed their invitations and enrolled
separate devices. Claude Code and Codex CLI loaded the Flopwire plugins in
scratch configurations.

## Messaging sequence and limits

Acceptance automation was explicitly authorized for the disposable accounts;
it supplies no evidence for the human acceptance workflow. A delivered or
read receipt alone does not prove that a model replied. Confirm the reply
through the receiving model's native context.

The repeat used one Claude stream-JSON process held open between turns. Its
pre-acceptance turn reported no hook message. After acceptance released one
request, the next turn received it in a native `UserPromptSubmit` hook
attachment and sent the exact authorized acknowledgment through the native
plugin MCP tool. The attachment timestamp was 18:27:20 UTC. The receipt
was queued for the live, busy Codex session's next tool call. The Claude turn
completed successfully with no permission denials. Return delivery was then
verified in the Codex native transcript: a developer message marked
`hooks.additional_context` at 18:30:10.900 UTC contains the exact reply and
original request reference. Codex completed its turn and reported receiving
that reply. Server records subsequently showed both messages as `read`.

The successful Codex headless send used persisted per-tool approval in the
scratch configuration. A custom MCP server named `qualification` launched the
candidate binary with `args = ["mcp"]` and forwarded the isolated
`FLOPWIRE_CONFIG` and `FLOPWIRE_INDEX` environment variables. Its
`tools.flopwire_send.approval_mode` was `"approve"`. Runtime overrides had
failed to enable the send. This qualifies the explicitly preapproved custom
MCP route; default headless plugin approval behavior remains unqualified.

The first attempt used separate Claude print/resume processes. The recipient
ran a pre-acceptance turn and exited, then acceptance released the held
message before another resume. The first post-acceptance turn received no
hook message at its prompt or its harmless tool call and made no send call.
The recipient agent logged one session-ended failure at 18:13:21 UTC.

The source contract explains why this sequence can end delivery:
[`internal/devicebus/ended.go`](../../internal/devicebus/ended.go) distinguishes
an idle process from an ended session. A SessionEnd hook or a registry entry
that no longer names a running process ends the session. Queued messages
created while the session looked live become `undelivered` with reason
`session_ended`, including messages that reach the device after that end.
The comparison uses the message's original creation time, rather than its
acceptance time. A later resume does not requeue an undelivered message.
Messages sent to a session already known to be inactive instead wait for a
resume, subject to expiry. The delayed-arrival behavior is covered by
`TestSessionEndedReportedToTheServer` in
[`internal/devicebus/ended_test.go`](../../internal/devicebus/ended_test.go).
The observed process exits and the original request's local message-bus row
confirm the session-ended path. The row reports `state=undelivered`,
`reason=session_ended`, `attempts=0`, `ack=done`, and `read_at=null`. The
completed acknowledgment records the device's failure report. A separate
server check confirmed `undelivered/session_ended`, with no delivery or read
time, for that original request.
