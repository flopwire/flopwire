# Vendor cloud delivery, 2026-10-03

Live checks behind issue #63 (plan decision B6, section 6): the request and
response shapes the adapters in `internal/vendorcloud` depend on, and the
end-to-end checks of push delivery into a Claude cloud session and a Devin
cloud session. Extends the cloud rows of
[`probes-2026-10-01.md`](probes-2026-10-01.md).

Versions: Claude Code 2.1.288, Devin CLI 3000.11.1. One scratch session per
vendor, on the cheapest model (Claude Haiku; Devin's default), created for
this check. No session ids or account identifiers are recorded here.

## Claude cloud sessions

### Discovery

The plan named `GET /v1/sessions`. It works, but it is not what the
adapter uses.

| Request | Result |
|---|---|
| `GET https://api.anthropic.com/v1/sessions`, `Authorization: Bearer <claude.ai OAuth access token>`, `anthropic-version: 2023-06-01`, `anthropic-beta: ccr-byoc-2025-07-29` | 200. `{"data":[…],"first_id","last_id","has_more"}`, newest created first, 200 per page by default, `limit` and `after_id` page it |
| The same without the `anthropic-beta` header | 404 `not_found_error` |
| Filters (`session_status`, `environment_kind`, `status`, `include_archived`, …) | Ignored: every query returned the same page |

Entry fields used or seen: `id` (`session_` + 24 characters),
`title`, `session_status` (`archived`, `idle`, `running`,
`requires_action`), `connection_status` (`connected`, `disconnected`),
`status_bucket`, `environment_kind`, `type` (`internal_session`),
`origin` (`claude_code_cli`), `session_context` (`sources`, `outcomes`,
`model`, `mcp_config`, …), `external_metadata`, `created_at`,
`updated_at`.

It lists every session of the account, including the local sessions
that Remote Control mirrors (`environment_kind: "bridge"`). For the test
account that was over 3,000 entries, almost all archived bridge sessions,
and 1 cloud session in the first 3,000. With no filter, discovery would
read the whole list every time.

The Claude Code CLI's own `--teleport` list reads another route, which
takes a status filter. The adapter uses it:

| Request | Result |
|---|---|
| `GET https://api.anthropic.com/v1/code/sessions?statuses=active&limit=100`, `Authorization: Bearer <token>`, `anthropic-version: 2023-06-01` (no beta header) | 200. `{"data":[…],"next_cursor","resume_token"}`; `cursor=<next_cursor>` pages it. 88 active sessions in one page, 3 of them cloud |
| `status=active`, `environment_kind=…`, `worker_status=…` | Ignored. Only `statuses` filtered |

Entry fields: `id` (`cse_` + the same 24 characters as the `session_`
id; 86 of 88 matched an entry of `/v1/sessions`, the other 2 were past the
3,000 read), `title`, `status` (`active`, `archived`), `worker_status`
(`running`, `idle`, `requires_action`), `connection_status`,
`environment_kind` (`bridge`, `anthropic_cloud`; the CLI also knows `byoc`
and `snap`), `status_bucket`, `created_at`, `updated_at`,
`last_event_at`, `user_message_count` (a string), `config` (`sources`:
`[{"type":"git_repository","url","revision",…}]`, `outcomes`, `model`,
`origin`, `effort_level`), `external_metadata` (`current_branches`:
`{"owner/name": "branch"}`, `worktree_state`, `context_usage`,
`rate_limit_info`), `tags`, `unread`, `participants`, `relations`.

The adapter keeps `environment_kind == "anthropic_cloud"` and
`status == "active"`, names the session by its `session_` id (the form
claude.ai URLs and `claude --teleport` use), and takes a turn as running
while `worker_status == "running"`. A scratch session reported `idle`
seconds after it answered, `running` within 2 s of a push, and `idle`
again at the end of the turn.

The token is the Claude Code login: on macOS the keychain item
`Claude Code-credentials` (`security find-generic-password -w`), else
`~/.claude/.credentials.json`; JSON `claudeAiOauth.accessToken` and
`expiresAt` (ms). The token lasts hours and Claude Code refreshes it when
it runs. Flopwire never refreshes it: a refresh rotates the refresh
token under Claude Code. Discovery stops while the token is expired.

### Delivery

`claude -p TEXT --cloud ID --output-format json` prints
`{"ok":true,"session_id":ID,"url":"https://claude.ai/code/session_…"}` and
exits 0 in about 3 s. Both id forms work. It loads the local Claude Code
plugins: a plugin's `SessionEnd` hook ran on each push. It writes no
local transcript.

`claude -p --cloud "<task>"` does not create a session: "--cloud cannot be
combined with --print. Starting a new cloud session with --cloud is
interactive only". The scratch session was created with an interactive
`claude --cloud "<task>" --model haiku` in a scratch git repo (it asked for
workspace trust first).

### Session events (read receipts)

`GET /v1/code/sessions/<cse_ id>/events?limit=N&sort_order=desc`, same
headers: `{"data":[{"sequence_num":"92","created_at","payload":{"type",
"subtype","message":{"role","content"}}}],"next_cursor","resume_cursor"}`.
`sequence_num` is a JSON string. Payload types seen: `user` (prompts,
pushed text and tool results), `assistant`, `system`, `tool_progress`,
`env_manager_log`, `result`, `rate_limit_event`, `active_goal`,
`autocompact_state`.

A pushed text is recorded as a `user` event when it is posted, also in
the middle of a tool call, before the model sees it. The model takes it
at the next tool result. Probe: a marker pushed at 18:26:58 during a 90 s
command; the next `assistant` event (18:28:02, after the command's
result) was the first model call with it, and the turn's final answer
quoted it. The read receipt is therefore the first `assistant` event after
the `user` event that carries the wrapper.

## Devin cloud sessions

Over `devin acp --cloud` (ACP, JSON-RPC 2.0, one message per line):

| Call | Result |
|---|---|
| `initialize` | about 0.6 s. `agentCapabilities._meta` lists Devin extensions (`sessionListExtendedFilters`, `queuedMessages`, …) |
| `session/list {}` | about 0.2 s. `{"sessions":[{"sessionId":"devin-<32 hex>","title","cwd":"","updatedAt","_meta":{…}}]}`; no cursor at 3 sessions |
| `session/new {"cwd":"/","mcpServers":[]}` | Creates a session. It is not listed until it gets a prompt |
| `session/prompt {"sessionId","prompt":[{"type":"text","text"}]}` | `session/update` `user_message_chunk` with the whole text within about 1 s, then `agent_thought_chunk` / `agent_message_chunk`; the answer (`stopReason: "end_turn"`) only when the turn ends |
| `session/load {"sessionId","cwd","mcpServers"}` | Replays the history as `user_message_chunk` and `agent_message_chunk` updates |

`_meta` keys used: `cognition.ai/creatorUserId`, `cognition.ai/isArchived`,
`cognition.ai/sessionStatus`, `cognition.ai/statusEnum`. Seen:
`sessionStatus` `new`, `running`, `suspended` (and `exited` in the
2026-10-01 probes); `statusEnum` `initializing`, `working` (a turn runs),
`blocked` (waiting for the user), `finished`; `statusReason`
`user_inactivity` on a suspended session. The list is the organization's:
the adapter keeps sessions whose `creatorUserId` is the "User ID" line of
`devin auth status`, not archived, not exited. A turn runs while
`statusEnum` is `working`.

Closing the relay while `session/prompt` waits does not cancel the turn:
the session went on `working` and finished the task. A prompt sent while
the session was `working` was answered within seconds, before the
running command ended ("Got MARKER-5521 — will run the curls after the
loop finishes").

### Sending from inside

A Devin cloud session reaches the internet: `curl` to
`https://flopwire.com` and `https://example.com` both returned 200 from
inside the scratch session. It could reach a public Flopwire server. It
has no `flopwire` CLI and no device credential, and v1 sets up neither,
so Devin cloud sessions receive only. The cloud instruction says that the
session cannot reply. Claude cloud sessions cannot reach a server at all
at the default network level (probes 2026-10-01).

## Live checks

`TestLiveCloud` (`internal/devicebus/cloud_live_test.go`, run with
`FLOPWIRE_CLOUD_LIVE=claude:<id>` or `devin:<id>`) runs the device bus
with the real adapters and no server. The server path (claim by one of
the person's devices, push, ack, `push_failed`) is covered by the
Postgres tests in `internal/bus/cloud_test.go` and the fake-server test in
`internal/devicebus/cloud_test.go`, not live.

| Check | Claude cloud | Devin cloud |
|---|---|---|
| Discovery lists the scratch session, marked cloud | Yes, idle | Yes, suspended |
| A message to it while it runs no turn stays queued (30 s, nothing pushed) | Yes (idle) | Yes (suspended: the stopped case) |
| After the test starts a turn, the message is pushed into it and delivered | Yes, 13 s after the turn began (the test lists every 5 s; the default is 20 s) | Yes, after the session resumed and the next listing showed it `working` |
| The wrapper arrives intact and the model reads its attributes | Yes: "DONE (Flopwire message received: LIVE-…, sender="own", intent="request")" | Yes: "LIVE-…: Flopwire relayed a message with sender="own" and intent="request" … I can't reply to that session from here." |
| Read receipt | Yes, from the session events: 1 min 29 s after delivery, when the running command returned | Yes, from the push: the first agent chunk after the echo, within the same second |

The first Claude run delivered but set no read receipt: the events route
writes `sequence_num` as a string, which the adapter rejected. Fixed, with
a test on the live shape; the second run above has the receipt.

## Not tested

- Repo `.claude/settings.json` hooks and `.mcp.json` inside a Claude cloud
  VM (needs a scratch GitHub repo with the Claude GitHub App).
- A Claude cloud VM that was fully reclaimed. The scratch session's VM was
  disconnected (`connection_status: disconnected`) between runs and took
  the push and resumed; that is a paused VM, not a reclaimed one.
- Cross-user delivery live (another person's accepted message into a cloud
  session). It follows the server's accept rule, which the Postgres tests
  cover.
- More than one page of either vendor's list.
